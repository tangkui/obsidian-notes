## **1️⃣ MySQL 高并发锁问题（Lock wait timeout exceeded）**

### **STAR 模板回答**

**场景（S）**  
高并发订单系统中，订单落库偶尔失败，报 `Lock wait timeout exceeded`。高并发下同一行或同一表被多个事务频繁访问，导致锁竞争。

**任务（T）**  
确保高并发场景下订单能够稳定落库，消除锁等待导致的失败。

**行动（A）**

1. **事务拆分**
    
    - 将大事务拆成小事务，核心写库逻辑使用 `REQUIRES_NEW` 独立提交，减少锁持有时间。
        
    - 示例：订单主表落库独立事务，明细表和库存更新拆分成不同事务。
        
2. **复合索引优化**
    
    - 针对查询条件设计复合索引，如 `(user_id, status, create_time)`，减少全表扫描，降低行锁冲突。
        
    - 避免单列索引导致回表和额外锁扫描。
        
3. **Spring Event 异步解耦**
    
    - 订单落库核心逻辑在主事务，非核心逻辑（通知、缓存刷新、统计）通过事件异步处理。
        
    - 降低同步写库压力，避免锁被长时间占用。
        

**结果（R）**

- 成功消除锁竞争导致的落库失败
    
- 高并发下系统稳定性大幅提升
    
- 订单落库成功率接近 100%
    

---

### **面试官可能追问及回答技巧**

|面试官可能追问|回答思路 / 技巧|
|---|---|
|为什么 `REQUIRES_NEW` 可以减少锁等待？|新事务独立提交，前一个事务不会阻塞后续事务，缩短锁占用时间。|
|拆分事务会不会影响数据一致性？|核心订单写库仍在主事务，异步处理非核心逻辑，通过事务顺序 + 事件最终一致性保证。|
|复合索引和单列索引有什么区别？|复合索引可覆盖多列查询条件，减少回表；单列索引在多列查询中可能无法覆盖。|
|Lock wait timeout 异常如何定位？|使用 `SHOW ENGINE INNODB STATUS`、`INFORMATION_SCHEMA.INNODB_LOCKS` 和慢 SQL 日志。|
|高并发下还会有其他问题吗？|可能有死锁，可结合事务重试机制 + 最小化锁粒度解决。|

---

### **技术原理 & 实操点**

- **InnoDB 锁机制**：行锁、间隙锁、Next-Key Lock
    
- **事务隔离级别**：保证一致性同时减少锁冲突
    
- **索引覆盖**：复合索引覆盖查询条件可避免额外行锁扫描
    
- **Spring Event**：异步事件驱动，解耦主逻辑与辅助逻辑

## **2️⃣ JVM OOM 故障排查**

### **STAR 模板回答**

**场景（S）**  
线上系统偶发 JVM OOM，影响服务稳定性。

**任务（T）**  
快速定位内存泄漏或异常占用对象，保证系统恢复。

**行动（A）**

1. **生成 HeapDump**
    
    - 命令：`jmap -dump:format=b,file=heap.hprof <pid>`
        
    - 低峰期生成，避免影响线上服务。
        
2. **使用 MAT 分析堆快照**
    
    - 查看 **Dominator Tree** 找到最大对象引用链
        
    - 查看 **Histogram** 找到大对象数量异常
        
3. **辅助使用 JVM 工具**
    
    - `jps` 查看 JVM 进程
        
    - `jstat` 查看内存使用与 GC 状态
        
    - `jcmd` 查看线程、堆、GC 详情
        
4. **分析原因**
    
    - 内存泄漏：对象被意外引用，无法 GC
        
    - 正常高占用：对象使用峰值，可 GC 回收
        

**结果（R）**

- 快速定位泄漏对象或异常内存占用
    
- 缩短故障排查时间
    
- 修复内存泄漏，线上服务稳定性提升
    

---

### **面试官可能追问及回答技巧**

|面试官可能追问|回答思路 / 技巧|
|---|---|
|HeapDump 会影响线上吗？|生成时会短暂停顿，线上可选择低峰期或远程 dump。|
|如何区分内存泄漏和高占用？|内存占用持续增长且 GC 无法释放即泄漏；正常峰值可回收为高占用。|
|MAT 分析重点？|Dominator Tree、Class Histogram、大对象引用链、泄漏 Suspect Report。|
|jstat 和 jcmd 区别？|jstat 查看内存/Gc指标，jcmd 可以执行堆 dump、GC、线程分析等命令。|
|OOM 的常见原因？|大对象缓存未清理、集合无限增长、线程泄漏、第三方库泄漏。|

---

### **技术原理 & 实操点**

- **JVM 内存结构**：Heap, Metaspace, Stack, Young/Old Generation
    
- **GC 机制**：Minor GC / Major GC / Full GC
    
- **MAT 分析方法**：Dominator Tree + Histogram + Reference Chain
    
- **JVM 工具使用**：jps/jstat/jcmd 配合使用定位内存问题

## **3️⃣ SQL 性能分析与优化**

### **STAR 模板回答**

**场景（S）**  
数据库在高并发下出现锁等待、慢 SQL，影响系统性能。

**任务（T）**  
快速定位数据库瓶颈，优化 SQL 和系统性能。

**行动（A）**

1. **监控与分析**
    
    - Performance Schema：监控锁等待、慢 SQL、事务状态
        
    - Percona Toolkit：分析锁热点、慢查询、执行计划
        
2. **优化措施**
    
    - 调整索引设计，提高查询效率
        
    - 热点数据缓存到 Redis，减轻 DB 压力
        
    - 优化 SQL 执行计划，避免全表扫描
        
3. **验证效果**
    
    - 使用 EXPLAIN 查看优化后的执行计划
        
    - 对比查询耗时、锁等待时间
        

**结果（R）**

- 锁等待和慢 SQL 大幅下降
    
- 系统吞吐量提升
    
- 系统整体稳定性增强
    

---

### **面试官可能追问及回答技巧**

|面试官可能追问|回答思路 / 技巧|
|---|---|
|Performance Schema 与慢 SQL 日志区别？|PS 实时统计锁/等待，慢 SQL 日志记录执行慢的 SQL，PS 提供更细粒度。|
|热点数据缓存策略？|write-through 或异步更新缓存，保证最终一致性。|
|优化索引后如何验证？|EXPLAIN 执行计划，查询扫描行数减少，耗时下降。|
|高并发 DB 压力表现？|锁等待增多、慢 SQL 多、事务回滚、连接池满、CPU/IO 占用高。|
|Percona Toolkit 用法？|pt-deadlock-logger 分析死锁，pt-query-digest 分析慢 SQL，pt-online-schema-change 在线改表。|

---

### **技术原理 & 实操点**

- **MySQL 性能监控工具**：Performance Schema、慢 SQL 日志
    
- **Percona Toolkit 功能**：慢 SQL 分析、锁分析、在线表改造
    
- **索引优化**：覆盖索引、复合索引、唯一索引
    
- **缓存策略**：热点数据缓存，减轻 DB 压力

## **4️⃣ RestTemplate NoHttpResponseException 排查**

### **STAR 模板回答**

**场景（S）**  
A 系统调用 B 系统接口偶发 `NoHttpResponseException`，线上接口不稳定。

**任务（T）**  
找出问题根因，提升接口调用稳定性。

**行动（A）**

1. **抓包分析**
    
    - 使用 tcpdump + Wireshark 捕获 TCP 流量
        
    - 发现空 body POST 请求被服务端 RST 重置
        
2. **调整请求**
    
    - 避免空 body POST
        
    - 调整参数位置和传输方式
        
3. **优化客户端**
    
    - 将 RestTemplate 替换为 Apache HttpClient
        
    - 提升连接复用与异常处理能力
        

**结果（R）**

- 接口调用稳定性大幅提升
    
- NoHttpResponseException 异常消失
    

---

### **面试官可能追问及回答技巧**

|面试官可能追问|回答思路 / 技巧|
|---|---|
|为什么空 body POST 会被 RST？|服务端期望有请求体，空 body 触发连接重置。|
|RestTemplate 和 HttpClient 区别？|HttpClient 支持连接池、超时控制、空 body 处理更稳定。|
|tcpdump / Wireshark 分析重点？|TCP 三次握手、FIN/RST、序列号、ACK 状态。|
|偶发问题怎么保证修复安全？|灰度验证、日志监控、fallback 方案。|
|还有哪些原因可能导致 NoHttpResponseException？|服务端超时、连接池耗尽、网络抖动、代理或中间件重置。|

---

### **技术原理 & 实操点**

- **TCP/IP & HTTP 协议**：三次握手、FIN/RST、连接状态
    
- **RestTemplate 限制**：默认连接池较小、空 body 异常处理弱
    
- **HttpClient 优势**：连接池管理、重试机制、异常处理
    
- **抓包分析**：定位低层 TCP 问题，精确到包级别
